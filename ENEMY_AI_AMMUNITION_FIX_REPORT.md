# VEILSTRIKE v4.2 — ENEMY AI, COMBAT BEHAVIOUR & AMMUNITION FIX REPORT

Scope: gameplay correction pass over the existing project — enemy combat behaviour, enemy
locomotion, ammunition accounting, and campaign ammunition pickups. No redesign, no new
engine, no systems replaced. Nothing was deployed and nothing was pushed.

---

## 0. How this build was verified (and what that does *not* cover)

All verification is **headless**: a Node loader (`tests/progress_test_loader.mjs`) imports the
real game modules — real `EnemyManager`, real `PhysicsWorld`, real `WeaponState`, real map
builders — and drives them frame by frame, asserting on trajectories measured from the executed
code (detection curves, turn rates, accelerations, round counters, HP deltas).

**There is no browser in this environment** (no Playwright/Chromium is available and none was
installed), so nobody has *watched* an enemy patrol, reload or pick up a crate. Statements about
how the game *looks* are therefore quantified properties (turn rate inside a cap, zero heading
reversals, 0 % wall-grinding frames, spacing margins), not visual sign-off. Where a requirement
is inherently visual — "clear visual identification" for pickups — it is verified **structurally**
(distinct tint + distinct label per ammunition family, asserted in B10) and not on screen.
Raw evidence for every claim is in `reports/*.txt`, regenerated by one command (§9).

## 2. Phase 1 — enemy combat state machine

States: `patrol → suspicious → alert → combat → (reposition) → search → patrol`, plus
`dead`. `js/enemies.js`.

**Detection is line-of-sight, not distance.** Recognition accrues from a model in
`_perceive()` (js/enemies.js:577) driven by the exported `AI_SENSE` block (js/enemies.js:55):

```
BASE_GAIN 1.55/s  ·  range term 1.12 − 0.72·(d/visionRange), floor 0.34
FOV cone (archetype `fov`, e.g. rifleman 108°) → full gain; clear sight but outside the
cone → PERIPHERAL_GAIN 0.5; blind side → BLIND_GAIN 0.16
LOS_FLOOR 0.8          clear sight line ⇒ eventually noticed from any angle
NEAR_FLOOR 0.9         up close, a crouching/low-signature player is still noticed
SPOT_THRESHOLD 0.62    the ONE threshold for "seen", used by the reflex turn and combat entry
RECALL_THRESHOLD 0.21  hysteresis: once engaged, memory tracks at a lower bar
ALARM_THRESHOLD 0.92   squad escalation trigger
```

`hasLOS(eye, chest)` (js/physics.js:600) raycasts the **same collider set the bodies move
against**, so a wall, crate or terrain ridge blocks sight and blocks fire. Visual range and FOV
are per-archetype config (`rifleman: vision 62, fov 108`; `recon: 82/128`; `marksman: 105/118`)
and the whole block is a live knob — test A4 halves/doubles `BASE_GAIN` and observes recognition
move accordingly.

**Reactions, not teleporting awareness.** An off-axis cue buys a *glance*: the body turns toward
it at `REFLEX_TURN 2.3 rad/s` within `REFLEX_ARC 1.9 ×` the half-FOV, and that reflex is measured
by the same turn-rate cap the movement suite uses (C2), so "turns to look" cannot become "spins".

**Suspicion and sound.** `hearNoise` (gunfire, suppressed differently, sprint/dog/radio events)
raises `detection` by distance and pushes a `suspicious` Investigate target at the noise source.
Squad members receive the report and escalate with a **bounded floor** (`0.24` suspicious,
`0.34` alert) instead of being switched to full awareness. A6 verifies a distant enemy reacts to
a shot he cannot see.

**Alert → immediately hostile, with discipline.** Combat entry requires crossing
`SPOT_THRESHOLD` while LOS holds. Firing then goes through `_combat` → weighted action selection
(hold/advance/reposition/flank) → `_aimAt` (rate-limited aim convergence; reaction delay
`reactionBase` clamped 0.30–1.60 s and scaled by skill, archetype and difficulty) → `_trigger` →
`_shoot`. The trigger re-checks `state === 'combat' && canSeePlayer && hasLOS` **at the moment the
shot leaves**, not merely at the aim tick — that is what makes "never shoots through walls" an
invariant rather than a coincidence (B3, D2).

One specific defect removed: the combat action was picked by
`if (this.rng() < dt * 0.36) this._trigger(...)` — roughly a 3 % per-tick chance to *attempt* a
shot, and only on arrival at a reposition destination. Heavies and marksmen, which reposition
often, could spend an entire engagement walking and never fire. The comment at
js/enemies.js:1354 records this; the weighted selector replaced it.

**Memory.** `lastKnown` position + timestamp. Losing sight goes to `search` at the last known
position, sweeping it, rather than resuming the patrol route (B8). `search` → `patrol` only after
the recall window expires.

**Dead.** `dead` halts movement, aim updates and trigger attempts, clears `canSeePlayer`/`hasLOS`
so a corpse cannot still pull a teammate's aim, and the body leaves `manager.list` after the death
animation (B9).

**Damage goes through the existing player health system.** `_shoot` resolves against
`player.applyDamage(...)` with the archetype weapon profile (damage, falloff, movement spread
penalty), so armour, standing/knockdown state, difficulty `damageTaken` and the existing HUD all
still apply (B1: a soldier in contact takes the player from full HP to damaged).

**Difficulty is a live knob on all of it** — verified, not assumed, by A7: with one rifleman and
a clear 20 m sight line, time to first hit is
`recruit 8.25 s → standard 5.18 s → hard 3.92 s → veteran 3.72 s`, from `DIFFICULTIES` in
js/progress.js (`skill / reaction / spread / detection / hearing / coverUse / coordination`).

## 3. Phase 2 — locomotion

The collision system was **not** weakened: `js/physics.js` is byte-identical to v4.1, the
collision suite grew to 33 checks and stays green, and the campaign-wide leak probe still reports
0 leak cells. Navigation was fixed by making the AI steer inside the existing collision
constraints.

Exported tuning block `AI_MOVE` (js/enemies.js:46):

```
ACCEL 7.5 m/s² · DECEL 10.5 m/s² · CALM_TURN 2.4 rad/s · ALERT_TURN 3.6 · COMBAT_TURN 6.0
REVERSAL_DWELL 0.35 s
```

- **Ramped speed.** `_move` integrates toward `_cmdSpeed` under the accel/decel cap and brakes for
  arrivals; the per-frame speed bound is `max(ACCEL, DECEL)`, which C1 asserts frame by frame.
  `moveSpeed` has exactly one writer (`_move`), so no other system can teleport the velocity.
- **Ramped turning.** Travel heading turns at the state-appropriate cap; aiming yaw is a separate,
  rate-limited value (`aimYaw`) that only feeds body yaw when the body has to follow it
  (`_aimAt`, body-follow), so a soldier no longer slides sideways while looking elsewhere (C4) and
  does not snap 180° between perception ticks (C3 counts heading reversals; C2 caps the *rendered*
  rate).
- **No pathological reversals.** A heading change greater than 135° must first be paid for with
  `REVERSAL_DWELL` of deceleration — a 180° flip now reads as a controlled about-face.
- **Obstacle avoidance / stuck recovery.** `_stuckRecover` (js/enemies.js:2227) detects no-progress
  against geometry and diverts or re-paths; `_setMoveTarget` records the commanded speed so the
  watchdog distinguishes "blocked" from "deliberately slow" (C6: a soldier pinned against geometry
  recovers instead of grinding). Contact separation from v4.1 is retained for spacing (C7) and
  state transitions do not teleport bodies (C8).
- **Deleted feedback loop.** `_driveRig` used to write the *presentation* yaw back into the AI's
  logical yaw — a third, unclamped yaw writer that produced visible spinning. It is now
  presentation-only and performs no AI writes (audited: yaw has 5 legitimate writers, all
  rate-limited or one-shot; see §7).

Development measurements from a temporary probe (the probe was removed; the properties are now
permanent invariants C1–C8): open ground 0 heading reversals, peak rendered turn 5.5 rad/s, 0 %
sliding, 0 wall-grinding frames; against a wall 3.5 rad/s with acceleration capped at 10.5 m/s²;
a 6-man squad converging: 2 reversals, worst spacing margin −1.49 m (i.e. bodies never
interpenetrating), 81 m travelled for 47 m of net progress, 0 wall-grinding frames; patrol
strafe share 12 %.

## 4. Phase 3 — one successful shot = exactly one bullet

**The accounting bug was not a duplicate shot.** Instrumentation of every firing path found no
double-fire and no per-pellet multi-decrement (M1 sweeps 176 cases — every weapon × semi/auto ×
60 Hz/144 Hz × click length — with **0 mismatches**). What was broken was the *economy around*
the counter, and the fix is in the model, not the display:

- `js/ui.js` was **not modified at all**. The HUD number is derived from the same store the weapon
  uses (`ammoHudState(def, st)`), and M6 asserts HUD↔model parity, so the displayed value cannot
  be prettier than the truth.
- Single entry point: `js/game.js:2496` is the only `tryFire` call in the codebase. `tryFire`
  gates (state `ready`, fire-mode ownership, cadence, malfunction, ammo) and **only then** calls
  `spendRound(def.id)` once (js/weapons.js:1681) before `stats.shots++`. M7 greps the shipped
  source for exactly this property.
- Single charge point: `spendRound(id)` (js/weapons.js:1481) takes no count argument and decrements
  `st.mag--` exactly once. Shotgun pellets loop over the hit roll, not the magazine (M9: one round,
  nine pellets).
- Nothing that is not a shot charges anything: muzzle flash, sound, recoil, hitscan, projectile
  creation are side effects only (M8 asserts side-effect counts track `stats.shots` while rounds do
  not move extra).
- Blocked/early/rejected presses consume nothing (M3), an empty magazine blocks firing and cannot
  go negative (M4), reload transfers exactly what both stores can hold and commits once
  (`_commitReload`, idempotent; M5), a dry reload and a tactical reload differ (M1 sweep covers both).
- The requested ladder, measured on the VX-4 in both modes:
  `300 → 299 → 298`, ten shots `→ 290`, fifty `→ 250`, a hundred `→ 200` — identical for semi and
  auto (M2).
- `Player.resupplyAll()` was the actual hole: it wrote
  `reserve = min(reserveMax, reserve + x)`, so a weapon with `reserveMax: 0` (the VX-4) could never
  be resupplied at all, while weapons with a reserve could be topped up past intent. It now routes
  through `addRounds` (js/player.js:749), the same owner the pickups use, and M12 asserts it cannot
  zero a loadout or exceed a cap.
- Magazine capacities, fire modes, RPM, reload times, pellet counts and the rest of the weapon
  table are **untouched**: M10 parses the shipped table and diffs it field by field against the
  pre-fix baseline recorded in `tests/baselines/weapons_v4.1.json` (generated from the accepted v4.1
  archive) and, where a git checkout exists, against `git show HEAD:js/weapons.js` — 12 weapons,
  0 field changes. The
  guard is known to bite: temporarily setting `mr7.rpm` to 144 makes M10 fail on both comparisons.
- Disclosed, not hidden: one *secondary* store writer remains by design — the LB-9 mission-allowance
  block (js/weapons.js:1661–1674, decrement at :1673) consumes `st.freeAllowance` and re-derives `mag + reserve` as
  a projection of it. M11 audits that projection (`mag + reserve === freeAllowance`, exactly one
  decrement per shot, no negative stores, `roundsSpent === shots`), so it is not a second charge.
- Enemy fire obeys the same rule: 24 shots debited 24 rounds with 5 forced reloads on a deliberately
  4-round magazine (B10); a dry soldier stops shooting and reloads (B5).

## 5. Phase 4 — campaign ammunition pickups

New module `js/ammo.js` holds the whole policy — one maintainable family table rather than
per-weapon hardcoding:

```
AMMO_TYPES   rifle(200 max, crate 80) · smg(240, 90) · support(240, 90) · marksman(160, 40)
             precision(40, 25) · shell(96, 32)
WEAPON_AMMO  vx4/cr9/rk4 → rifle · mr7/sz8 → marksman · lb9 → precision
             vekp/mpx5/p9 → smg · st12/vx12 → shell · hmg9 → support
AMMO_PACK_SIZES  [10, 20, 30, 40, 50]      normalisePackRounds() snaps to that table
grantPack(game,{type,rounds}) → {granted, wasted, perWeapon, label}   single owner
grantCrate(game) → one bounded family allocation (equipped family, else next owned with room)
```

**Placement.** `placeCampaignAmmoPacks()` (js/campaign-maps.js) is called from one choke point —
the end of `GameWorld.buildByMap` — after `_ensureCollisionCoverage()` has finished, because the
per-map builders and the campaign generator both run before `world.physics` exists. Candidates are
seeded where they belong (patrol route waypoints, cover points, the objective terminal's apron),
then a coarse grid so a route-less map still gets supplies. Each candidate must pass:

- `packGroundY` — a short low probe requiring an upward-facing surface (`normal.y > 0.4`), so a
  pack never hangs under a catwalk or floats;
- `packSpotIsGood` — the pack's own volume free of solid geometry **and**, at 1.2 m around it, one of
  8 bearings where a standing player volume is free *and* has a clear eye→pack line (so you can
  actually stand at it, face it and see it);
- ≥ 3.5 m from the player spawn, ≥ 4.5 m from other packs, and clear of vehicle parking. If
  physics is not available the placer returns nothing at all — it never ships unvalidated packs.

`GameWorld._settleAmmoPacks(physics)` re-measures the surface after the final world build, ring
searches 3 radii × 12 bearings for a legal seat, and if none exists **withdraws** the pack (hidden
and spliced out) rather than shipping an unreachable or buried collectible. Placement never
retries after a refusal: `used` is only set when rounds were actually granted.

**The pickup itself.** A decorative tin (`noCollider: true`, family-tinted lid, its own
`PointLight`) plus an interactable with `radius 1.5`, prompt `TAKE 30 RIFLE AMMO`, and `F` to
collect. Collecting shows `+30 RIFLE AMMO`, plays the pickup sound, and updates the HUD from the
same store (B1, B2). Family mismatch is a hard refusal (B3: a SHOTGUN pack never feeds a rifle and
vice versa), over-cap is clamped with the remainder reported as wasted (B4), and a pack can never
be collected twice (B5, plus a self-guard inside the action so the rule does not depend on the
caller). A pack you cannot use yet stays available instead of being silently eaten (B6).

**Distribution and balance.** Every one of the 100 campaign operations gets supplies (P1) —
**531 packs, 15,000 rounds** total, 5.3 per mission, scaling with the operation: 33 packs across
OP 001–010 versus 62 across OP 091–100 (P3), with the size ladder weighted upward the same way:
`+10 ×51, +20 ×139, +30 ×200, +40 ×134, +50 ×7` (P2 — only these five values exist anywhere).
133 of the 531 are deliberately off the direct route and count as optional exploration rewards
(P7). Counting the legacy crates, the campaign places **450 field crates**, and each now issues
**one bounded family allocation (25–90 rounds by family)** instead of a full `resupplyAll()`
refill — B11 — because once Phase 3 repaired `resupplyAll`, five crates per mission would otherwise
have amounted to unlimited ammunition, which is explicitly out of scope for a "balance preserved"
brief. There is no other ammunition income: no kill drops, no loot tables (grepped), and every
mission starts from the def loadout scaled by the difficulty's `reserve` multiplier (recruit 1.3×,
veteran 0.7×), so supplies genuinely matter on the harder settings.

Objectives, spawn logic, mission defs and progression data are untouched; P9 asserts the legacy
hand-built maps keep working crates and gain nothing broken, and the campaign audit still reports
100/100 completable operations.

## 7. Phase 6 — integration inspection of the final code

- **Duplicate firing paths: none.** One `tryFire` call site (js/game.js:2496); one charge function
  (`spendRound`, no count parameter); `stats.shots` incremented only immediately after a successful
  charge. Asserted both by grep (M7) and by the 176-case behavioural sweep (M1).
- **Conflicting enemy AI updates: none remain.** `EnemyManager.update` is called from exactly two
  mutually exclusive branches of the frame loop — js/game.js:2511 (playing) and js/game.js:2671
  (the `DEAD` state's death cam) — and PAUSED/COMPLETE/FAILED return before either. Inside
  `js/enemies.js`, audited writer counts: `yaw` ← constructor, two rate-limited perception turns,
  one body-follow, one travel turn; `aimYaw` ← constructor, two spot solves, `_aimAt`; `moveSpeed`
  ← `_move` only; `combatAction` ← `_combat` only; `detection` ← one accrual site plus bounded squad
  floors and the decay paths. The presentation layer (`_driveRig`) writes no AI state.
- **Collision and vehicle systems from v4.1: intact.** `js/physics.js`, `js/vehicles.js`,
  `js/impacts.js` unchanged; 33/33 collision checks, 97.65 % coverage, 0 leaks in 112 maps, and the
  vehicle/boarding suite all green.
- **Nothing removed.** 12 weapons (`WEAPON_ORDER`), 100 operations, 20 environment categories,
  4 difficulty presets (recruit / standard / hard / veteran), training range, vehicles, touch controls,
  soundtrack and both deployment configs are all present; requirement checks 15/15 and the campaign
  audit 5/5 pass.
- **Packaging check found and fixed a real shipping break:** `js/ammo.js` was not in the service
  worker PRECACHE list, so an offline/returning client could have failed to boot. Added, and the
  cache version bumped; `python3 tests/module_delivery_smoke.py` then reports 41 modules served as
  JavaScript with the audio registry intact.
- Not done, per instructions: no deployment, no push, no new dependencies, no project replacement.

## 10. Known limitations

1. **No visual verification.** Everything above is headless. In particular "movement looks
   controlled", "enemies behave believably" and "pickups are clearly identifiable" are asserted as
   measured properties (turn-rate caps, reversal counts, per-family tint + label), not confirmed on
   screen. A human pass in a browser is still the last word.
2. **Sight is occluded by level geometry, not by actors.** `hasLOS` raycasts the static collider set
   (v4.1 design), so soldiers do not blind each other in a corridor — but that also means an enemy
   can see you over a truck bed or past another body. Changing it would alter v4.1 combat spacing,
   so it was left alone deliberately.
3. **Residual contact jitter under crowding.** With a 6-man squad converging on one spot, commanded
   acceleration can momentarily exceed the steering ramp (46–56 m/s² measured) because `processMoveContacts`
   separation — not steering — moves the body. It never interpenetrates and never exceeds the
   per-frame speed bound the suite asserts, but under extreme crowding a soldier can look shoved
   rather than walked.
4. **Patrol strafe share 12 %** measured in development: patrol paths legitimately sidestep around
   props; the combat case is 0 %. Not classified as a bug, but it is the kind of thing a visual pass
   may still want re-tuned.
5. **`+50` packs are rare by construction** (7 in the campaign, top bracket only). The table allows
   all five increments everywhere; the distribution is deliberately bell-shaped so pickups do not
   trivialise ammo.
6. **The LB-9 keeps its mission-allowance store**, so `mag + reserve` is a projection of
   `freeAllowance` for that weapon rather than an independent pair of counters. It is audited (M11)
   and behaves correctly, but any new tooling that reads only `mag`/`reserve` must use
   `roundsNeeded`/`ammoAvailable` instead of assuming capacity.
7. **Enemy marksmen/heavies reposition a lot**, so their observed fire cadence is lower than a
   rifleman's at equal range. That is the intended Phase-1 behaviour (weapon-specific cadence,
   suppressed while moving via the movement spread penalty), but it can read as "the heavy is lazy"
   on a small map.
8. **Crates are family-agnostic but family-bounded**: one crate feeds one family per opening
   (equipped if it has room, else the next owned family with room). If *every* family you carry is
   full, the crate refuses and stays available — you will see `AMMUNITION FULL` rather than losing
   it.
9. `reports/COLLISION_VERIFICATION_MATRIX.md` documents the collision suite (33 rows). The AI,
   ammunition and pickup suites print their own per-check lines into `reports/*.txt`; a combined
   matrix for those three is not generated.
